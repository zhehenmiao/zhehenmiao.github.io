多 Agent 协作系统

个人项目 · 2026.10 – 2026.11

问题

一个人同时用几套 AI 编程工具，它们各说各的、互相打架、活干一半就停。没有人盯着的时候，错误会被当成完成。

派活链路原来还是阻塞式的：一次派发要等 305 秒，超时就重发，重发又会打断对方。等待时间和互相干扰叠在一起，活越派越慢。没有闸门时，错误会被当成完成；派发没有异步状态，就只能阻塞等待。

方案

四台机器分工：调度中枢跑调度逻辑，Linux 执行机跑代码生成，GitHub 私有仓做唯一产物权威，网络出口负责翻墙调用。执行机只改文件、不碰 .git，提交权集中在调度侧，防止残留进程偷偷提交。

全链路拆成九步：写契约 → 路由判活 → 派发 → 执行 → 确定性验收 → 模糊项判定 → 签字 → 合并 → 记账。

合并前过三层闸门：第一层确定性检查，用命令行量具输出数字；第二层 Jev 语义判定，给判定模型喂实测数据，而不是「我觉得对了」；第三层人工复核签字。任何一层不过就不合并。

派活改成异步：投递后立刻返回，状态异步回查，不再阻塞等待或靠重发打断对方。

结果

305s → 8.9s
任务派发耗时。投递后立即返回、状态异步回查，不再阻塞等待或超时重发打断对方
一条命令
跑完全链：契约 → 确定性检查 → 语义判定 → 入队 → 复核 → 合并 → 记账
每单证据包
每条检查的实测数字都随单留存，复核和记账可以直接对账
3 层
闸门：确定性检查 → Jev 语义判定 → 人工复核签字 任何一层不过就不合并

踩过的坑

这三条是这套系统最值钱的部分：

  1. 读不出数据却盖了 OK 章 —— 磁盘检查脚本对 /proc 拿到 -，算术比较判假，直接走了「正常」分支并返回 0。修法：取值后先校验形状，不是数字就报错退出。
  2. 变异测试改错了地方 —— 要求「故意改坏一处看测试会不会红」，但改的那行本来就走不到，测试当然不红。修法：变异后全部用例仍绿时，标记为「可能等价变异」而不是直接判失败。
  3. 多个会话同时写同一个仓库 —— 一个会话的改动被另一个覆盖过一次。修法：动笔前先 pull --rebase，改已有段落前先看 git log，冲突留现场。
